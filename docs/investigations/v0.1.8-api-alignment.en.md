# v0.1.8 API and documentation alignment audit

[中文](v0.1.8-api-alignment.md) · [日本語](v0.1.8-api-alignment.ja.md)

Audit date: 2026-09-07. Release baseline: `91406690405f87f03b9ddddbc48179426bf5abea` (v0.1.8); fixes based on `3d79d0d87c363576b3aeb9ecfc6a3ea8f9834653`.

## Findings and fixes

v0.1.8 had binding and documentation omissions; it cannot be described as aligned on every platform. This work does not change the playback core.

| Area | Finding | Action |
|---|---|---|
| OpenHarmony Flutter | Dart sends `videoAlphaMode`, but ArkTS and N-API create functions discarded it, so the core always received opaque | Added fourth argument and type declarations; old three-argument calls still default to opaque |
| Standalone OHPM SDK | Neither configuration interface nor N-API create function had a transparent-video parameter | Added optional configuration and forwarded it to `ErikaPresenterConfig.video_alpha_mode` |
| Header copies | OHPM copy lacked Windows Flutter texture getters; Flutter copy was correct | Synchronized with the main header. These are Windows-only getters, not missing OHOS runtime functionality |
| Trilingual C API documentation | Omitted Windows texture getters and described synchronous open as asynchronous | Added interfaces, COM reference ownership, error behavior and synchronous open constraints |
| ABI documentation | v0.1.7 configuration is 12 bytes and v0.1.8 is 16 bytes; by-value calls cannot mix them | All three references explicitly require rebuilding matching headers, bindings and library together |
| Architecture and Flutter docs | Hard-coded 88 functions; some platform lists omitted Windows texture | Removed stale count, clarified Windows-only export boundary, synchronized platform descriptions in three languages |
| Japanese screenshot docs | Contradictory text said both “without danmaku” and “with danmaku” | Aligned with implementation and English/Chinese: video plus subtitles, no danmaku |
| Standalone liberika-swift SDK | main still binds v0.1.7, create uses a three-field configuration and public open has no read-ahead argument | Confirmed but not fixed in this repository; requires a separate SDK upgrade commit and Apple build validation |

Core wgpu's `video_uniforms_for_frame`, logical video width and transparent clear already consume alpha mode. OHOS AVCodec Vulkan conversion continues into that composition path, so the missing parameter occurs in the binding layer. This does not establish real-device acceptance of an OHOS transparent window or Flutter compositor.

## PR scope

The 29 merged PRs between v0.1.7 and v0.1.8 were checked by category:

- APIs, bindings and GPU composition: #105, #119, #123, #124, #126, #127, #128, #129. #127/#128 fixed Apple config mirrors; this work fills the OHOS argument and the header copy omitted after #129.
- Core playback behavior: #82, #115, #121, #122, #131. No new C entry points are required; these fixes are unchanged here.
- Artifacts, SDK publication and documentation: #98, #99, #100, #101, #102, #103, #104, #106, #108, #109, #110, #111, #112, #113, #114, #117. Successful packaging and binary/device runtime validation on each platform are different conclusions.

Seven C functions were added in this version: two `open_with_options`, `create_with_output_mode_and_alpha`, `attach_flutter_texture`, `set_flutter_texture_buffer` and two Windows `IUnknown` getters. The main header's 98 functions match Rust export names and argument/return types; the check includes platform implementations and unsupported-platform stubs in source (opaque presenter pointers treated as ABI-equivalent). It does not prove every struct layout or link result for every target.

The new `ErikaOpenOptions` field order and widths match Rust and handwritten mirrors on all three Apple platforms: headers pointer, pointer-width count, u64 read-ahead and three u64 reserved fields. Updated `ErikaPresenterConfig` is i32/f32/i32/i32; Apple mirrors match. Windows and Android creation bindings forward alpha mode; HTTP read-ahead is handled by Apple, Windows, Android and OHOS JSON paths.

## Validation and limits

- Five targeted tests passed: header mirrors, function names, C/Rust function signatures, ArkTS argument chain, and simulated host execution of both original N-API `NativeCreate` functions.
- The original create-function test directly compiles the repository functions and checks fake N-API input and a presenter capture endpoint: four-argument alpha=1, three-argument default alpha=0, preservation of other config and rejection with fewer than three arguments. Both old v0.1.8 functions failed at the alpha=1 assertion; the fixed versions passed. This is not a substitute for an OHOS N-API SDK build or real-device run.
- `llvm-nm -D --defined-only` on `liberika_capi.so` in the downloaded v0.1.8 `erika-capi-openharmony-arm64.zip` found all 96 expected C symbols and no additional C symbols. The two `erika_presenter_windows_*_iunknown` exports are Rust Windows-cfg-only and should not appear on OHOS.
- Full symbol tables of the other released platform libraries were not read in this round; no comprehensive guarantee is made for those unchecked artifacts.
- Independent `AimesSoft/liberika-swift` main `96159140b3be7cd4623ffb6f4d009502422d66ae` was checked via GitHub API: the `Package.swift` binary target still pointed to v0.1.7; `ErikaPlayer.swift` created a three-field config, and public open had HTTP headers but no read-ahead. It used its matching old library, so this does not establish runtime ABI mixing, but it was not yet aligned with v0.1.8. Changing only the download URL is insufficient: config initialization and public parameters must also be updated and Apple builds validated.
- `git diff --check` passed. Regression checks were added to the existing Ubuntu quality job without a new CI matrix; this round did not trigger remote CI or modify released v0.1.8 artifacts.

Local execution: `CXX=g++ python3 packaging/tests/test_api_alignment.py -v`. The fix only reaches registry users after a subsequent merge and release of Flutter/OHPM packages containing updated ArkTS and N-API bridges; updating the core library alone cannot fix arguments lost by old bridges.
