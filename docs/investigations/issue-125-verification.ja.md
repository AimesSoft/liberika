# Issue #125：リソースライフサイクルの修正と検証

[中国語の記録](issue-125-verification.zh.md)の翻訳です。検証環境：2026-09-28、macOS / Apple Silicon、コミット `ca40a95` を基準とするブランチ。Issue：https://github.com/AimesSoft/liberika/issues/125

## 結論

問題は存在しましたが、2 つの挙動を区別する必要があります。

- `stop()` は先頭からの再生し直しのために再生セッションとデコーダーを意図的に保持していました。停止後に一部メモリが残ることは従来の仕様です。
- HTTP の永続先読み worker と非同期 demux worker では所有権の終了処理が決定的ではありませんでした。HTTP worker の `JoinHandle` は破棄され、デストラクターはフラグを設定するだけで、レスポンスヘッダーや本文の読み込み中にブロックするとフラグを確認できません。`AsyncDemuxer` もスレッドハンドルを保存せず、破棄時に `Stop` を送信するだけでした。このため破棄が返った後も接続、スレッド、メディアソースが残り得ます。このライフサイクル不具合は再現しました。

元の報告者のホストアプリで「数百 MB が常駐する」という全体の推移は再現しておらず、Swift の強参照リークも確認していません。プロセス footprint が直ちに起動時の値に戻らないことだけでは、オブジェクトが生存している証拠になりません。

## 修正

- フォアグラウンドの Range 要求と永続先読みを共有 reqwest / Tokio I/O runtime で実行します。各メディアソースは generation 付きキャンセルトークンを持ち、キャンセル時に要求 future を破棄して connect、TLS、レスポンスヘッダー・本文の待機を中断します。システムのブロッキングリゾルバーに入った DNS 処理は独立して完了する可能性があり、その同期終了は保証しません。
- フォアグラウンド要求のヘッダー待ち上限は 15 秒、本文でデータが連続して来ない場合の待ち上限は 60 秒です。各要求は fetch 全体の残り予算にも制限され、リトライ、バックオフ、HEAD から GET へのフォールバックの合計は最大 120 秒です。フォールバック GET は残予算とヘッダー待ち上限の小さい方を使います。
- 永続ストリームは既存の単一接続、ストライプの引き渡し、ウィンドウのバックプレッシャー設計を保持します。各ストリームセッションは worker の `JoinHandle` を保存し、セッションの `Drop` が I/O をキャンセルして worker を起こし、終了を待ちます。worker の全終了経路で先読みを待つフォアグラウンドスレッドに通知し、ソケット閉鎖後に待ち続けることを防ぎます。
- `AsyncDemuxer` は `JoinHandle` とメディアソースのキャンセルハンドルを保存します。seek は旧 generation の読み込みを中断し、worker が seek を処理してから新 generation を再開します。破棄時は終端キャンセルを行ってスレッドを待ち、満杯の packet channel に worker が詰まらないよう待機中に channel を排出します。
- `stop()` は再生し直し可能なまま、復帰前に HTTP キャッシュ、永続先読み、空の再生キュー容量を解放します。既存の `open()` は旧セッションを置換し、`close()` / destroy はメディアリソースを解放します。半閉鎖 API は追加しません。

変更範囲は source、demux ライフサイクル、必要な依存関係に限定しています。reqwest / Tokio は依存サイズを増やしますが、ネットワークでブロック中の同期 FFmpeg 読み込みをキャンセル可能にします。スレッドハンドルを保存して join するだけでは、ネットワーク待ちがデストラクターに持ち込まれます。C API、JNI、JSON ブリッジ、Player、Presenter の公開ライフサイクル API は変更していません。malloc pressure relief や強制的なアロケーター回収で生存リソースを隠していません。

## 実験

### 修正前の実 TCP 対照

ローカルサーバーが有効な 206 ヘッダーと 8 MiB の本文サイズを返し、本文は送らない設定にしました。当時の `main` の `HttpRangeSource` で永続ストリームを開始して直後に破棄すると、破棄が返ってから 500 ms 以内にサーバーは EOF を観測せず、回帰テストは安定して失敗しました。worker とソケットがソースオブジェクトの寿命を超えて生存することを示しています。

修正後、同じテストは安定して通過しました。ソースの破棄はソケット閉鎖と worker 終了を待ちます。

### キャンセル、再生し直し、終了

`crates/erika/tests/media_lifecycle.rs` は実 TCP / HTTP 接続とリポジトリの MKV サンプルを使い、次を検証します。

- HEAD、レスポンスヘッダー、レスポンス本文、TLS ハンドシェイクのブロック中にキャンセルでき、サーバーが EOF / reset を観測する。
- ソース破棄または `release_buffer()` で先読みがキャンセルされ、解放後も認証ヘッダーを保って再読み込みできる。
- 実 Player で HTTP 読み込み中に連続 seek、stop 後の再生し直し、open による旧セッション置換、close を実行する。
- demux の破棄がメディアソース解放を待ち、packet キューが満杯でもデッドロックしない。

今回の TLS、HEAD、レスポンスヘッダー、本文のキャンセル所要時間はそれぞれ 0.17、0.04、0.06、0.08 ms。Player の stop、open による旧セッション置換、close はそれぞれ 0.01、3.38、0.23 ms でした。テスト上限は 500 ms で、これらのローカル値は他のデバイスでの遅延を保証しません。

追加の `cancellation_wakes_a_reader_waiting_for_prefetch` 回帰は前版 `9c8300c` で 500 ms 内にキャンセル結果を受け取れず失敗しました。終了通知を補い、条件確認と待機で同じロックを使う修正後に通過しました。

### タイムアウトとリトライ

実 TCP を使う 6 件のテストは、テスト専用の短いタイムアウトを使って本番と同じ実行経路を検証します。

- HEAD が 405 または長さ 0 を返すと、フォールバック GET は HEAD のリトライで消費済みの総予算を引き継ぐ。
- 初回 HEAD / GET が停止すると、単一レスポンスのタイムアウトが発生し、実際に 2 回目の要求を送って結果を得る。
- 本文が一部到着後に停止した場合、旧接続を解放し、受信済みオフセットから `If-Range` を付けて再開する。
- 本文が継続的に到着する場合、ヘッダー待ち期限を超えてもよいが、データが届き続けても総予算は超えられない。

旧タイムアウトロジックのまま短いテスト予算のみを注入すると最初の 5 件すべてが失敗し、修正後は 6 件すべて通過しました。ライフサイクルテストでは EOF、`ConnectionReset`、`ConnectionAborted` を有効な切断として扱い、Windows で返り得る中止種別をカバーします。今回の実行環境は macOS であり、Windows での再検証は未実施です。

### メモリ

macOS の単一プロセス実験ではリポジトリの MKV、ソフトウェアデコード、64 KiB HTTP ウィンドウを使い、player 作成 → open → play → stop → close を 12 回繰り返しました。各サンプルの前にテストホストが保持するフレームを解放しています。

| 段階 | live malloc バイト | footprint バイト |
|---|---:|---:|
| 初期基準 | 621,648 | 3,260,800 |
| 1 回目の再生 | 2,341,024 | 7,356,848 |
| 1 回目の停止 | 1,675,312 | 7,979,440 |
| 1 回目の終了 | 717,552 | 7,881,112 |
| 12 回目の停止 | 1,675,312 | 8,815,024 |
| 12 回目の終了 | 717,552 | 8,700,312 |

12 回の close 後の live malloc はすべて **717,552 バイト**で、回ごとの蓄積はありませんでした。footprint は起動時の基準に戻りませんでしたが、アロケーター、共有 HTTP runtime、システムフレームワークが仮想 / 物理ページを保持する挙動と整合します。footprint 単独ではリークを判定できません。

## 検証コマンド

```sh
cargo test -p erika -p erika_capi --lib
cargo test -p erika --test media_lifecycle -- --nocapture --test-threads=1
cargo test -p erika --test media_lifecycle memory_probe -- --ignored --nocapture --test-threads=1
```

結果：liberika のライブラリテスト 681 件、C API テスト 41 件がすべて通過。ライフサイクル統合テスト 4 件と手動メモリ実験 1 件も通過しました。

## 限界

元の報告者のホスト、長時間・高ビットレートの公衆 HTTPS、VideoToolbox / Metal の完全なメモリ推移、全ターゲットのビルドは未検証です。ホストに渡されたフレームは引き続きホストが解放する必要があります。ブロッキング I/O を持つサードパーティの独自 `MediaSource` は、独自のキャンセルハンドルを実装する必要があります。追加した Rust 依存の各プラットフォームでのコンパイルは CI での検証が必要です。
